# Workflow Studio Native Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a reproducible Tauri/Svelte application shell with tests, CI, a typed native boundary, a versioned authoring-contract loader, and LOOP24 default resources.

**Architecture:** Svelte owns presentation, pure TypeScript owns application contracts, and a thin Tauri/Rust host exposes typed native capabilities. A browser bridge makes renderer behavior testable without Tauri. Production workflow fields come only from bundled Hermes authoring contracts.

**Tech Stack:** Tauri 2.11.5, Rust 1.88.0+, Svelte 5.56.8, TypeScript 6.0.3, Vite 8.1.5, Nanostores 1.4.1, YAML 2.9.0, Ajv 8.20.0, Vitest 4.1.10, Svelte Testing Library 5.4.2.

## Global constraints

- Execute from the standalone `workflow-studio` repository on a feature branch created from `base`.
- Preserve all existing documentation and the `base` branch history.
- Use Node `>=22.12.0`, npm `>=10`, and Rust `>=1.88.0`.
- Use the neutral bundle identifier `com.cmetech.workflowstudio`; LOOP24 is the build-time/default display brand.
- Do not add Electron, SvelteKit, a local HTTP server, Python, or a Hermes runtime dependency.
- Keep route/shell components thin and shared state in feature-owned Nanostores.
- Rust may expose native capabilities but may not implement workflow-language rules.
- Do not create a production contract by copying Hermes field constants. Test fixtures may be intentionally minimal.
- All network-independent tests must run offline after `npm ci` and `cargo fetch` have populated caches.

- [ ] **Step 1: Define exact contract types**

Define the reader-facing envelope:

```ts
export type WorkflowProfile = 'hermes-legacy' | 'archon-2026-07'

export interface AuthoringContract {
  schema_version: 1
  contract_reader_version: number
  profile: WorkflowProfile
  normalizer_version: number
  contract_digest: `sha256:${string}`
  definition_schema: Record<string, unknown>
  sidecar_schema: Record<string, unknown>
  node_kinds: readonly NodeKindDescriptor[]
  semantic_rules: readonly SemanticRuleDescriptor[]
  compatibility_codes: Readonly<Record<string, CompatibilityDescriptor>>
  documentation: ContractDocumentation
  limits: { max_document_bytes: number }
  extensions: Readonly<Record<string, unknown>>
}
```

The descriptor interfaces must include stable IDs, labels/descriptions, field paths, applicability, widgets, order/section, status, examples, and rule parameters described in the design. Do not create production field data in these types.

- [ ] **Step 2: Write failing loader tests**

Test:

- supported reader/schema/profile succeeds;
- byte-identical input returns the same digest/provenance;
- digest mismatch fails with `contract_digest_mismatch`;
- unsupported schema/reader version fails with `contract_reader_unsupported`;
- unknown profile fails with `contract_profile_unsupported`;
- absent definition/sidecar schema fails with `contract_shape_invalid`;
- unknown top-level envelope keys are preserved in `extensions` but never interpreted; and
- loading performs no network or native calls.

- [ ] **Step 3: Run loader tests to verify failure**

Run:

```bash
npm run test:unit -- src/lib/contract/contract-loader.test.ts
```

Expected: FAIL because loader functions are absent.

- [ ] **Step 4: Implement canonical digest verification**

Canonicalize the parsed envelope with `contract_digest` omitted: recursively sort object keys, preserve array order, and serialize primitives through `JSON.stringify`. Hash UTF-8 bytes with Web Crypto SHA-256 and compare lowercase hex in constant normalized form.

Return a discriminated result rather than throwing untyped errors:

```ts
export type ContractLoadResult =
  | { ok: true; contract: AuthoringContract; source: ContractSource }
  | { ok: false; code: ContractLoadErrorCode; message: string }
```

`loadAuthoringContract(bytes, source)` returns `Promise<ContractLoadResult>` because SHA-256 uses Web Crypto. Unrecognized top-level envelope keys are copied into the reader-only `extensions` mapping and never treated as language behavior.

Fixtures are deliberately small contract-reader tests and must say `test_fixture: true` under an extension key. `contracts/README.md` states that production contract files are generated from Hermes and may not be manually authored.
